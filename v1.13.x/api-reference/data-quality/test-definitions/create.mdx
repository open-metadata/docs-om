# Create a Test Definition

Create a custom test definition to define organization-specific data quality validation logic.

## Body Parameters

<ParamField body="name" type="string" required>
  Name of the test definition. Must be unique across all test definitions.
</ParamField>

<ParamField body="displayName" type="string">
  Human-readable display name for the test definition.
</ParamField>

<ParamField body="description" type="string">
  Description of what this test validates, in Markdown format.
</ParamField>

<ParamField body="entityType" type="string" required>
  The entity type this test targets: `TABLE` or `COLUMN`.
</ParamField>

<ParamField body="testPlatforms" type="array" required>
  Array of supported test platforms. Typically `["OpenMetadata"]`.
</ParamField>

<ParamField body="supportedDataTypes" type="array">
  Array of data types this test can be applied to, for example `STRING`, `INT`, `DOUBLE`, `VARCHAR`, `CHAR`, `TEXT`, `NUMBER`, `FLOAT`, `BOOLEAN`. Only applicable when `entityType` is `COLUMN`.
</ParamField>

<ParamField body="parameterDefinition" type="array">
  Array of parameter definitions that this test accepts.

  <Expandable title="properties">
    <ParamField body="name" type="string" required>
      Name of the parameter.
    </ParamField>

    <ParamField body="dataType" type="string" required>
      Data type of the parameter, for example `INT`, `STRING`, `BOOLEAN`, `ARRAY`, `TABLE`.
    </ParamField>

    <ParamField body="required" type="boolean">
      Whether this parameter is required when creating a test case. Defaults to `false`.
    </ParamField>

    <ParamField body="description" type="string">
      Description of the parameter.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body="sqlExpression" type="string">
  SQL template for custom SQL-based test definitions. OpenMetadata renders the template with Jinja2, so every placeholder must use double curly braces:

  - `{{ table_name }}`: the table the test case runs against.
  - `{{ column_name }}`: the column the test case runs against. Available only when `entityType` is `COLUMN`.
  - `{{ paramName }}`: the value of a parameter declared in `parameterDefinition`.

  OpenMetadata doesn't substitute single-brace placeholders, which produce invalid SQL. The test passes only when the rendered query returns 0 rows. `table_name` is reserved for all definitions, and `column_name` is also reserved when `entityType` is `COLUMN`. Don't use reserved names as parameter names. For more information, see [Custom SQL Test Definitions](#custom-sql-test-definitions).
</ParamField>

<ParamField body="validatorClass" type="string">
  Class name of the validator that runs the test. For a custom SQL test definition, set one of the following values. The OpenMetadata UI sets the same values when you create a custom SQL test definition:

  - `ColumnRuleLibrarySqlExpressionValidator`: use when `entityType` is `COLUMN`.
  - `TableRuleLibrarySqlExpressionValidator`: use when `entityType` is `TABLE`.

  Built-in test definitions use their own validators, which you can't select for a custom definition. The server accepts any string for this field, so always set it explicitly for SQL-based definitions.
</ParamField>

<ParamField body="dataQualityDimension" type="string">
  Data quality dimension the test belongs to: `Completeness`, `Accuracy`, `Consistency`, `Validity`, `Uniqueness`, `Integrity`, `SQL`, or `NoDimension`.
</ParamField>

<ParamField body="supportedServices" type="array">
  Names of the services this test definition supports. When empty, all services are supported. Defaults to `[]`.
</ParamField>

<ParamField body="domains" type="array">
  Fully qualified names of the domains the test definition belongs to.
</ParamField>

<ParamField body="owners" type="array">
  Array of owner references (users or teams) to assign.

  <Expandable title="properties">
    <ParamField body="id" type="string">
      UUID of the owner entity.
    </ParamField>

    <ParamField body="type" type="string">
      Type of owner entity, for example `user`, `team`.
    </ParamField>

    <ParamField body="name" type="string">
      Name of the owner entity.
    </ParamField>
  </Expandable>
</ParamField>

<RequestExample dropdown>
```python POST /v1/dataQuality/testDefinitions
from metadata.sdk import configure
from metadata.sdk.entities import TestDefinitions
from metadata.generated.schema.api.tests.createTestDefinition import CreateTestDefinitionRequest

configure(
    host="https://your-company.open-metadata.org/api",
    jwt_token="your-jwt-token"
)

request = CreateTestDefinitionRequest(
    name="columnValuesMaxLength",
    displayName="Column Values Max Length",
    description="Fails when a value is longer than the allowed length",
    entityType="COLUMN",
    testPlatforms=["OpenMetadata"],
    dataQualityDimension="SQL",
    supportedDataTypes=["STRING", "VARCHAR", "TEXT"],
    sqlExpression="SELECT * FROM {{ table_name }} WHERE LENGTH({{ column_name }}) > {{ maxLength }}",
    validatorClass="ColumnRuleLibrarySqlExpressionValidator",
    parameterDefinition=[
        {
            "name": "maxLength",
            "dataType": "INT",
            "required": True,
            "description": "Maximum allowed length"
        }
    ]
)

test_def = TestDefinitions.create(request)
print(f"Created: {test_def.name.root}")
```

```java POST /v1/dataQuality/testDefinitions
import java.util.List;
import org.openmetadata.schema.api.tests.CreateTestDefinition;
import org.openmetadata.schema.tests.TestCaseParameter;
import org.openmetadata.schema.tests.TestPlatform;
import org.openmetadata.schema.type.ColumnDataType;
import org.openmetadata.schema.type.TestCaseParameterDataType;
import org.openmetadata.schema.type.TestDefinitionEntityType;

// client is an initialized OpenMetadataClient.
var request = new CreateTestDefinition()
    .withName("columnValuesToMatchBusinessRule")
    .withDisplayName("Column Values To Match Business Rule")
    .withDescription("Validates that column values conform to a custom business rule regex pattern")
    .withEntityType(TestDefinitionEntityType.COLUMN)
    .withTestPlatforms(List.of(TestPlatform.OPEN_METADATA))
    .withSupportedDataTypes(List.of(
        ColumnDataType.STRING, ColumnDataType.VARCHAR, ColumnDataType.TEXT))
    .withParameterDefinition(List.of(
        new TestCaseParameter()
            .withName("regexPattern")
            .withDataType(TestCaseParameterDataType.STRING)
            .withRequired(true)
            .withDescription("The regex pattern to match against"),
        new TestCaseParameter()
            .withName("threshold")
            .withDataType(TestCaseParameterDataType.INT)
            .withRequired(false)
            .withDescription("Maximum number of non-matching values allowed")));

var testDefinition = client.testDefinitions().create(request);
```

## Custom SQL Test Definitions

A custom test definition is a reusable SQL template. To run a one-off SQL query on a single table, such as the **Custom SQL Query** test type in the UI, create a test case with the built-in `tableCustomSQLQuery` definition instead. For more information, see [Custom SQL Test Cases](/v1.13.x/api-reference/data-quality/test-cases/create#custom-sql-test-cases).

To create a test definition that runs your own SQL, set `sqlExpression` and declare every `{{ paramName }}` placeholder in `parameterDefinition`. The following request creates a column-level test that fails when any value in the column is longer than a limit:

```bash
curl -X POST "{base_url}/api/v1/dataQuality/testDefinitions" \
  -H "Authorization: Bearer {access_token}" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "columnValuesMaxLength",
    "displayName": "Column Values Max Length",
    "description": "Fails when a value is longer than the allowed length",
    "entityType": "COLUMN",
    "testPlatforms": ["OpenMetadata"],
    "dataQualityDimension": "SQL",
    "supportedDataTypes": ["STRING", "VARCHAR", "TEXT"],
    "sqlExpression": "SELECT * FROM {{ table_name }} WHERE LENGTH({{ column_name }}) > {{ maxLength }}",
    "validatorClass": "ColumnRuleLibrarySqlExpressionValidator",
    "parameterDefinition": [
      {"name": "maxLength", "dataType": "INT", "required": true, "description": "Maximum allowed length"}
    ]
  }'
```

How OpenMetadata evaluates the SQL:

- **Pass condition**: The test case passes only when the rendered query returns 0 rows. Write the query so that it returns the rows that violate the rule.
- **Reserved names**: `table_name` is reserved for table-level definitions. `table_name` and `column_name` are reserved for column-level definitions. Do not declare them in `parameterDefinition`, because the validator supplies their values at runtime.
- **Parameters**: A test case supplies values for `{{ paramName }}` through `parameterValues`. For more information, see [Create a Test Case](/v1.13.x/api-reference/data-quality/test-cases/create#custom-sql-test-cases).

## Create or Update (PUT)

Use `PUT /v1/dataQuality/testDefinitions` instead of `POST` to perform an upsert. If a test definition with the same name already exists, it will be updated; otherwise, a new test definition is created. The request body is the same as `POST`.

```bash
curl -X PUT "{base_url}/api/v1/dataQuality/testDefinitions" \
  -H "Authorization: Bearer {access_token}" \
  -H "Content-Type: application/json" \
  -d '{ ... same body as POST ... }'
```

<Note>
`PUT` will not return a `409` conflict error if the entity already exists. It will update the existing entity instead.
</Note>
