# OpenMetadata Standards

OpenMetadata Standards is the community-driven home for the schemas and ontologies behind OpenMetadata. It provides the canonical JSON Schemas, RDF/OWL models, and API specifications that power data cataloging, governance, lineage, quality, and observability.

Key highlights:

- **Comprehensive coverage**: 700+ JSON Schemas spanning entities, relationships, events, and configuration.
- **API-first**: REST and event schemas for search, feeds, webhooks, and bulk operations.
- **Semantic web ready**: RDF/OWL ontologies and SHACL shapes for knowledge graph and linked data use cases.
- **Standards compliant**: JSON Schema (Draft 07/2020-12), RDF/OWL, SHACL, JSON-LD, PROV-O.
- **Community driven**: Built and maintained by the OpenMetadata community with open governance.

## Schemas

The OpenMetadata standard is powered by [JSON Schemas](https://json-schema.org/), as a readable and language-agnostic
solution that allows us to automatically generate code for the different pieces of the project.

**2.** If you prefer to stay in the docs, we also have you covered. We have converted the JSON Schemas to markdown files

    In this generation we wanted to maintain the same structure as the GitHub repository. Any empty file means that you reached
    a directory, but you can keep exploring until finding the right Entity, or you can also look for it using the Search Bar.

## Machine Learning & Data Governance Expansion

The following terms bridge common machine learning and data governance concepts to business-friendly language, with payments-domain examples showing how each one shows up in practice.

### Model Drift

* **Technical Definition**: The degradation of a predictive model's performance over time due to shifts in underlying input data distributions or relationships between variables.
* **Business Translation**: A decrease in decision accuracy because real-world customer behaviors or market conditions have changed since the model was trained.
* **Payments Example**: A fraud detection model flags fewer fraudulent card transactions because bad actors adopted new transaction splitting techniques not present in the historical training data.

### Data Lineage

* **Technical Definition**: The complete record of data origins, transformations, movement, and dependencies across upstream and downstream systems.
* **Business Translation**: An audit trail showing exactly where data came from, how it was processed, and where it ended up.
* **Payments Example**: Tracing a settled merchant payout back through settlement engines, gateway logs, and raw ISO 8583 message feeds to resolve a balance discrepancy.

### Feature Engineering

* **Technical Definition**: The process of using domain knowledge to extract, transform, and aggregate raw data into variables suitable for machine learning models.
* **Business Translation**: Converting raw transaction logs into meaningful business indicators that help algorithms make smarter decisions.
* **Payments Example**: Transforming raw timestamps into indicators like "number of international card attempts in the last 10 minutes" to assess fraud risk.

### Label Skew

* **Technical Definition**: Label skew occurs when the proportion or baseline distribution of target labels in the training dataset differs significantly from the ground-truth distribution encountered in production.
* **Business Translation**: The training data assumes a certain baseline outcome frequency, but operational or market changes alter how often those outcomes happen in real-world traffic.
* **Payments Example**: A fraud detection model trained on historical data where 1% of transactions were fraudulent experiences label skew when expanding into a high-risk region causes the true production fraud rate to jump to 5%.

### Data Quality SLA (Service Level Agreement)

* **Technical Definition**: Formal metrics and thresholds that define acceptable parameters for data accuracy, completeness, freshness, and delivery timelines.
* **Business Translation**: An operational rule setting minimum standards for data reliability and delivery times to keep business workflows running smoothly.
* **Payments Example**: A requirement that end-of-day transaction settlement feeds arrive by 02:00 UTC with 0% missing transaction IDs.
