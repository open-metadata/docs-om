# Configuration Reference Parameters

## Public Key Url (publicKeyUrls):
This needs to be updated as per different SSO providers. The default value is `http://localhost:8585/api/v1/system/config/jwks`. This is the URL where the public keys are stored. The public keys are used to verify the signature of the JWT token.

<Warning>

**Google**: https://www.googleapis.com/oauth2/v3/certs

**Okta**: https://dev-19259000.okta.com/oauth2/aus5836ihy7o8ivuJ5d7/v1/keys

**Auth0**: https://dev-3e0nwcqx.us.auth0.com/.well-known/jwks.json

**Azure**: `https://login.microsoftonline.com/{tenant}/discovery/v2.0/keys`

Also if you have enabled [JWT Tokens](/v2.1.x-SNAPSHOT/deployment/security/enable-jwt-tokens) then `http://localhost:8585/api/v1/system/config/jwks` also needs to be there in the list with proper server url.

</Warning>

## Client ID (id):
The client ID provided by your OIDC provider. This is typically obtained when you register your application with the OIDC provider.

## Type (type):
Specify the type of OIDC provider you are using (e.g., google, azure). This value is same as `provider` in `authenticationConfiguration`.

## Client Secret (secret):
Replace with the client secret provided by your OIDC provider.

## Scope (scope):
Define the scopes that your application requests during authentication. Update `${OIDC_SCOPE:-"openid email profile"}` with the desired scopes.

<Tip>

It does not need to be changed in most cases. The default scopes are `openid email profile`. The openid scope is required for OIDC authentication. The email and profile scopes are used to retrieve the user's email address and profile information.
Although, some provider only give Refresh Token if `offline_access` scope is provided. So, if you want to use Refresh Token, you need to add `offline_access` scope, like below:
`offline_access openid email profile`.

</Tip>

## Discovery URI (discoveryUri):
Provide the URL of the OIDC provider's discovery document. This document contains metadata about the provider's configuration.

<Warning>

It is mostly in the format as below: https://accounts.google.com/.well-known/openid-configuration

**Google**: https://accounts.google.com/.well-known/openid-configuration

**Okta**: https://dev-19259000.okta.com/oauth2/aus5836ihy7o8ivuJ5d7/.well-known/openid-configuration

**Auth0**: https://dev-3e0nwcqx.us.auth0.com/.well-known/openid-configuration

**Azure**: `https://login.microsoftonline.com/{tenant}/v2.0/.well-known/openid-configuration`

Normally it's some initial SSO provider URL followed by `.well-known/openid-configuration`

</Warning>

## Use Nonce (useNonce):
Set to true by Default, if you want to use nonce for replay attack protection during authentication. This does not need to be changed.

## Preferred JWS Algorithm (preferredJwsAlgorithm):
Specify the preferred JSON Web Signature (JWS) algorithm. Default is RS256 and need not be changed .

## Response Type (responseType):
Define the response type for the authentication request. Default is code and need not be changed.

## Disable PKCE (disablePkce):
Set `${OIDC_DISABLE_PKCE:-true}` to true if you want to disable Proof Key for Code Exchange (PKCE). If you want to send CodeVerifier and CodeChallenge in the request, set it to false.

## Callback URL (callbackUrl):
Provide the callback URL where the OIDC provider redirects after authentication. Update `${OIDC_CALLBACK:-"http://localhost:8585/callback"}` with your actual callback URL.

<Warning>

The only initial part of the URL should be changed, the rest of the URL should be the same as the default one. The default URL is `http://localhost:8585/callback`.
Also, this should match what you have configured in your OIDC provider. Register the `/callback` endpoint in your provider, not `/auth/callback`.

</Warning>

## Server URL (serverUrl):
Specify the URL of your OM Server. Default is `http://localhost:8585`.

## Client Authentication Method (clientAuthenticationMethod):
Define the method used for client authentication. Default is client_secret_post.

<Warning>

This does not need to be changed in most cases. The default value is `client_secret_post`.
This method is used to send the client ID and client secret in the request body.
Another possible value is `client_secret_basic`, which sends the client ID and client secret in the Authorization header.
Depending on the OIDC provider, you may need to change this value if only one of them is supported.

</Warning>

## Tenant (tenant):
If applicable, specify the tenant ID for multi-tenant applications. Example in case of Azure.

<Warning>

This is only applicable for multi-tenant applications. If you are using a single tenant application, you can leave this field empty.
For Azure SSO Provider this may be needed.

</Warning>

## Max Clock Skew (maxClockSkew):
Define the maximum acceptable clock skew between your application server and the OIDC server.

## Max Age (maxAge):
The `max_age` request parameter, in seconds, that OpenMetadata sends to the identity provider. Update `${OIDC_MAX_AGE:-""}` to set it.
Default: empty. Leave it empty so the identity provider can reuse its own session. A value of `0` is treated as not set. To force users to re-enter their credentials, set `prompt` to `login`.

## Prompt (prompt):
Controls what the identity provider displays during login: `none`, `login`, `consent`, or `select_account`. Update `${OIDC_PROMPT_TYPE:-""}` to set it.
Default: empty. Leave it empty unless you need to force a specific behavior. OpenMetadata sends `none` itself when it re-authenticates a user silently.

## End Session With Provider (endSessionWithProvider):
Available for confidential OIDC clients only. Set `${OIDC_END_SESSION_WITH_PROVIDER:-false}` to true to tie a user session to the identity provider's session.
Default: `false`
When true, OpenMetadata renews the identity provider's tokens on the provider's schedule while the user is active. It signs the user out when the provider rejects the refresh token. The token that OpenMetadata issues is shortened to that schedule, with a minimum of 120 seconds. A renewal never extends the session beyond the configured session expiry. When false, a session lasts for the configured session expiry. The sign-out depends on the provider: Keycloak revokes refresh tokens together with the provider session, and Microsoft Entra ID doesn't.

## Use Roles From Provider (useRolesFromProvider):
Whether to derive roles from the authentication provider. Roles must be included in the identity provider's token and must match existing OpenMetadata role names. OpenMetadata skips any role name it doesn't recognize.

Whether a role change at the provider reaches OpenMetadata depends on how the user signs in:

- **OIDC sign-in**: OpenMetadata updates the user's roles each time they sign in, so a role added or removed at the provider takes effect at their next sign-in. If the token doesn't include a roles claim at all, OpenMetadata treats it as no roles, because some providers leave the claim out once a user's last role is removed. Admin access follows the provider's `Admin` role, except for users listed in `adminEmails` (or the deprecated `adminPrincipals`).
- **SAML sign-in**: Signing in doesn't update roles from the provider. Manage these users' roles in OpenMetadata directly.

The provider can make a user an admin, and removing the Admin role at the provider removes their admin access at the next sign-in. A user listed in `adminEmails` (or the deprecated `adminPrincipals`) keeps admin access, because OpenMetadata restores it for everyone on those lists when they sign in. To remove it, remove the user from the list.

## Initial Admins (initialAdmins):
List of initial admin users for the system

## JWT Principal Claims (jwtPrincipalClaims):
**Definition:** The JWT claims OpenMetadata uses to identify the authenticated user.

<Note>
**Deprecated.** Use `emailClaim` instead. This setting keeps working until email-first identity turns on, which happens when you set `emailClaim` without `jwtPrincipalClaimsMapping`.
</Note>

For more information, see [Email-First User Identity](#email-first-user-identity).

**Example:**

```yaml
["preferred_username", "upn", "email", "sub"]
```

**Why it matters:** OpenMetadata evaluates this list in order and uses the first
matching claim to identify the user. If none match, authentication fails.

<Note>
**Note:** At least one claim in this list must correspond to the user's **email
address** — OpenMetadata uses this to identify and match authenticated users to
their accounts. Use `email` for consistency and compatibility; for domain
scoping, use the `hd` claim.
</Note>

<Note>
**Note:** If you are using Keycloak or Azure, avoid changing the order of
claims in `jwtPrincipalClaims` for existing deployments. The system relies
on claim order to match users in tokens to existing user records — changing
the order can cause authentication failures.
</Note>

**Common claim values by provider:**

| Provider | Recommended claims |
|---|---|
| Okta | `["preferred_username", "email", "sub"]` |
| Auth0 | `["preferred_username","email", "sub"]` |
| Azure | `["preferred_username","email", "sub"]` |
| Amazon Cognito | `["cognito:username", "email", "sub"]` |
| Custom OIDC | `["email", "preferred_username", "sub"]` |
| Keycloak | `["preferred_username","email", "sub"]` |
| OneLogin | `["preferred_username","email", "sub"]` |
| SAML | `["preferred_username","email", "sub"]` |
| LDAP | `["preferred_username","email", "sub"]` |

## JWT Principal Claims Mapping (jwtPrincipalClaimsMapping):
**Definition:** Maps JWT claims to OpenMetadata user profile fields. From OpenMetadata 2.0.6, the session tokens that OpenMetadata issues after sign-in carry the username and email that this mapping resolves, so API calls stay authenticated when your provider uses a custom username claim.

<Note>
**Deprecated.** Use `emailClaim` and `displayNameClaim` instead. If this setting is present, OpenMetadata keeps using the legacy flow even when `emailClaim` is set.
</Note>

**Supported keys:** Only `email` and `username` are valid mapping targets
in `jwtPrincipalClaimsMapping`.

**Example:**

```yaml
["email:email", "username:preferred_username"]
```

**Why it matters:** Controls how SSO login data maps to user profiles in OpenMetadata.

**Format:** `openmetadata_field:jwt_claim` (for example, `"email:email"`).

<Note>
**Note:** The display name is derived automatically from standard OIDC/JWT
claims — you don't need to configure it using `jwtPrincipalClaimsMapping`.
</Note>

If you need richer name handling, make sure your identity provider is configured to include `given_name` and `family_name` as claims in the ID token — OpenMetadata will pick them up automatically. Refer to your identity provider's documentation for instructions:

| Provider | How to enable `given_name` and `family_name` |
|---|---|
| Okta | Ensure `profile` scope is requested. See [OpenID Connect & OAuth 2.0 — Scopes and Claims](https://developer.okta.com/docs/api/openapi/okta-oauth/guides/overview) |
| Auth0 | Included automatically when `profile` scope is requested. See [ID Token Structure](https://auth0.com/docs/secure/tokens/id-tokens/id-token-structure) |
| Azure | Must be added as optional claims in App Registration → Token configuration. See [Configure optional claims](https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims) |
| Google | Included automatically when `profile` scope is requested. See [OpenID Connect — Sign in with Google](https://developers.google.com/identity/openid-connect/openid-connect) |
| Amazon Cognito | Must be enabled as standard attributes in the User Pool. See [Working with user attributes](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-attributes.html) |
| Keycloak | Included automatically when `profile` scope is requested. See [Securing Applications and Services Guide](https://www.keycloak.org/docs/latest/server_admin/index.html#_client_scopes) |
| OneLogin | Included automatically when `profile` scope is requested. See [Scopes — OpenID Connect](https://developers.onelogin.com/openid-connect/scopes) |
| SAML | Refer to your IdP's documentation to add `given_name` and `family_name` as assertion attributes |
| LDAP | Ensure `givenName` and `sn` attributes are populated on user entries in your directory |

<Warning>
**Important:** Using any other key (for example, `name` or `firstName`) will
cause the service to fail on startup with a validation error.
</Warning>

## Email-First User Identity

Starting in 2.1, OpenMetadata can identify a signed-in user by their **email address** instead of resolving a username from several token claims. The email address becomes the single key for finding an existing account. OpenMetadata generates the username from the email. For example, `john.doe@company.com` becomes `john.doe`. If that name is already taken, OpenMetadata appends a random suffix, for example `john.doe_x7k2`.

Email-first identity is opt-in. It turns on when you set `emailClaim` and have no `jwtPrincipalClaimsMapping` configured. Until then, OpenMetadata keeps using `jwtPrincipalClaims` as before, so upgrading without changing your configuration doesn't change how users are matched.

| Deprecated setting | Replace with |
|---|---|
| `jwtPrincipalClaims` | `emailClaim` |
| `jwtPrincipalClaimsMapping` | `emailClaim` and `displayNameClaim` |
| `adminPrincipals` | `adminEmails` |
| `principalDomain` | `botDomain` for bots, `allowedEmailDomains` to restrict sign-in |
| `enforcePrincipalDomain`, `allowedDomains` | `allowedEmailDomains` |

Deprecated settings keep working until their replacement takes over. For `jwtPrincipalClaims`, that happens when you set `emailClaim` and have no `jwtPrincipalClaimsMapping` configured. OpenMetadata logs a deprecation warning at startup only after you configure the replacement.

### What Email-First Identity Changes

When email-first identity is on:

- OpenMetadata rejects unknown emails instead of guessing. If no account matches the email in the token, but another account already uses the same name as the start of that email, sign-in fails with a `401`. This stops an unregistered email from acting as another user.
- Deactivated accounts can't sign in. OpenMetadata doesn't restore or update a deactivated (soft-deleted) user when their email appears in a token.
- OpenMetadata rejects unverified emails. It refuses an OIDC token that explicitly has `email_verified: false`. A token without the claim is accepted.
- OpenMetadata updates display names only when the provider sends one. A display name that a user customized in OpenMetadata isn't overwritten by a value built from their email.
- Self-signup follows `allowedEmailRegistrationDomains` for OIDC and SAML. LDAP self-signup follows it on every deployment, as described in [Changes That Apply to Every Deployment](#changes-that-apply-to-every-deployment).
- `allowedEmailDomains` applies to tokens from your identity provider. Tokens issued by OpenMetadata itself, such as session tokens and personal access tokens, skip the check. This keeps the default admin and long-standing users signed in even if their email domain isn't on the list.

### Identity Provider Subject Binding

On a user's first OIDC sign-in with email-first identity, OpenMetadata records the provider's unique subject (`sub`) identifier on the user. If a later sign-in presents the same email with a different subject, OpenMetadata refuses the sign-in instead of giving the person the existing account. This protects against a provider reassigning a former employee's email address to a new person.

- OIDC binds the subject. SAML and LDAP don't, because SAML name IDs often change at each sign-in and LDAP has no subject.
- Existing users bind automatically at their next OIDC sign-in. No migration is needed.
- If you legitimately move to a new identity provider that issues new subjects, an administrator must clear the stored subject first. For more information, see [Fix a User's Email Address](#fix-a-users-email-address).

### Fix a User's Email Address

You can't change a user's email through the UI or API. Use the `openmetadata-ops.sh` tool instead. Run it from your OpenMetadata installation:

```bash
./bootstrap/openmetadata-ops.sh change-email \
  --email old.address@company.com \
  --new-email new.address@company.com
```

Add `--clear-identity-binding` to also remove the recorded provider subject, so the user's next sign-in binds again. Use it when the address now belongs to a different person.

Before turning on `emailClaim`, find accounts whose email was generated by OpenMetadata rather than supplied by your provider. These accounts have an address like `user@principalDomain` that won't match a real address:

```bash
./bootstrap/openmetadata-ops.sh list-synthesized-emails
```

Use `-d` / `--domain` to list a specific domain. Then correct each account with `change-email`.

### Changes That Apply to Every Deployment

These happen on upgrade to 2.1 whether or not you turn on email-first identity:

- Stored emails become lowercase. The 2.1.0 migration lowercases every user email. Any script or integration that compares emails with case sensitivity sees the new values. No two users can collide because of this.
- MySQL email matching ignores accents. `jose@x.com` and `josé@x.com` now match as the same address.
- LDAP sign-in changes. Deactivated accounts can't sign in anymore. `allowedEmailRegistrationDomains` now applies to LDAP self-signup. A username collision gets a generated suffix instead of failing. The display name is synced from the directory, which overwrites a display name the user customized in OpenMetadata.
- `POST /v1/users` renames on a collision. For providers other than basic auth, a username that is already taken gets a generated suffix instead of returning a conflict error.

## Email Claim (emailClaim):
**Definition**: The name of the token claim that holds the user's email address. Setting it turns on email-first identity, unless `jwtPrincipalClaimsMapping` is also configured.

**Example**: `email`

**Environment variable**: `AUTHENTICATION_EMAIL_CLAIM`. Default: empty, which keeps the legacy `jwtPrincipalClaims` behavior.

## Display Name Claim (displayNameClaim):
**Definition**: The name of the token claim that holds the user's display name. OpenMetadata reads it only when `emailClaim` is set.

**Example**: `name`

**Environment variable**: `AUTHENTICATION_DISPLAY_NAME_CLAIM`. Default: empty.

## Admin Emails (adminEmails):
**Definition**: Email addresses of users who get administrator access. Replaces `adminPrincipals`.

**Example**: `["admin@company.com"]`

**Environment variable**: `AUTHORIZER_ADMIN_EMAILS`. Default: `[]`.

`adminEmails` matches users by email. The deprecated `adminPrincipals` still matches existing users by name, so upgrading doesn't create duplicate admin accounts.

## Allowed Email Domains (allowedEmailDomains):
**Definition**: Email domains allowed to sign in. When empty, all domains are allowed.

**Example**: `["company.com", "subsidiary.com"]`

**Environment variable**: `AUTHORIZER_ALLOWED_EMAIL_DOMAINS`. Default: `[]`.

## Bot Domain (botDomain):
**Definition**: The email domain OpenMetadata uses for bot accounts it creates, for example `ingestion-bot@{botDomain}`. Replaces `principalDomain` for bots.

**Environment variable**: `AUTHORIZER_BOT_DOMAIN`. Default: empty.

## Enable Self Signup (enableSelfSignup):
Allows users to sign up themselves if not already registered

## Preferred JWT Algorithms (preferredJwsAlgorithm):
Preferred algorithm for JWT signature validation

## Allowed Email Registration Domains (allowedEmailRegistrationDomains):
Specifies allowed domains for email registration
