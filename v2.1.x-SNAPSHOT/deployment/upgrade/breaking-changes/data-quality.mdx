# Data Quality & Observability

Upgrading from 2.0 to 2.1 changes how test cases are validated and how data quality dimensions are
stored. Most other changes are additive.

## Data Quality Dimensions Are Now Managed Entities

<Warning>
**Breaking for typed clients, behavioural for everyone else.** Affects code generated from the 2.0
schemas, the Python and Java SDKs, and scripts that set a test definition's dimension.
</Warning>

In 2.0 a dimension (Completeness, Accuracy and so on) was a fixed list of values. In 2.1 each dimension
is its own record that you can add to, rename or recolor under **Settings** > **Preferences** > **Data
Quality**. OpenMetadata ships seven system dimensions (Accuracy, Completeness, Consistency, Integrity,
SQL, Uniqueness and Validity) that cannot be edited or deleted.

```diff
  // testDefinition.dataQualityDimension
- "$ref": "#/definitions/dataQualityDimensions"   // fixed list of values
+ "$ref": "basic.json#/definitions/entityName"    // the name of any dimension, system or custom

  // testCase
+ "dataQualityDimension": { "$ref": "entityReference.json" }
```

What this means for you:

- `dataQualityDimension` on a test definition is now a plain name string, not an enum. Generated models
  that expected the old enum type must be regenerated.
- Test cases now carry their own `dataQualityDimension`. If you do not set one when you create a test
  case, it takes the dimension of its test definition. `CreateTestCaseRequest` accepts the new field.
- The upgrade first creates the system dimensions, then gives every existing test case that has no dimension the one its test definition names (marked as inherited, so reclassifying the definition later moves those test cases too). Test cases that already have a dimension are left alone. Test cases whose definition has no dimension or names an unknown one stay without a dimension, and appear under "No Dimension" in dashboards. If this step fails, the upgrade still finishes and the failure is only logged.

<Tip>
Regenerate any models or clients built from the 2.0 schemas. Code that compared a definition's
dimension against the old list of values keeps working for the seven system names, but no longer sees
an enum.
</Tip>

## New Test Cases Are Checked Against Their Definition

<Warning>
**Breaking for integrations that create test cases.** A request that used to be stored as sent can now
be rejected.
</Warning>

When you create a test case, OpenMetadata now rejects it if:

- a parameter that offers a fixed list of values (for example `thresholdUnit`, or the `strategy` of a
  custom SQL test) is given a value that is not in that list. The comparison ignores letter case, and a
  blank value counts as not set.
- the test targets a column whose data type the test definition does not support. A definition with no
  listed data types still supports every type.

In 2.0 these test cases were stored and then failed or measured nothing when the test ran. The check runs when a test case is created with `POST /v1/dataQuality/testCases` (the UI, API clients and
the MCP create tool). Updates are checked only for what they change, so test cases you already have
stay editable.

<Note>
In 2.1 the check is not applied to create-or-update calls (`PUT`) or to CSV import, so test cases sent
that way are still stored as before and can still fail when the test runs.
</Note>

<Tip>
If an automation creates test cases and starts receiving `400` errors after the upgrade, compare the
parameter values and the column type against the test definition. Test cases created from dbt or Great
Expectations are not affected because they create their own definitions without these limits.
</Tip>

## Set Parameters on "in set" and "not in set" Tests

<Note>
**Behavioural.** Affects `columnValuesToBeInSet` and `columnValuesToBeNotInSet`.
</Note>

- Values written as a JSON list (for example `[false, true]`) are now accepted. In 2.0 a JSON list with
  lowercase `true`, `false` or `null` aborted the test.
- On a column of type BOOLEAN, the text values `"true"` and `"false"` (any letter case) are compared as
  real booleans.
- A value that is not a list, such as a bare string or number, now aborts the test with an error. Wrap
  single values in a list.

## Table Column Set Test Honours `ordered: "false"`

<Note>
**Behavioural.** Affects `tableColumnToMatchSet`.
</Note>

In 2.0, setting `ordered` to the text `"false"` was treated as `true`, so the test compared column order
anyway. In 2.1 `"false"` means order is ignored. Tests that relied on the old behaviour and passed only
because the order matched keep passing. Tests that were failing because of the order may now pass.

## Failed Rows Sample Is Kept When a Test Passes Within Its Threshold

<Note>
**Behavioural.** Affects what you see on a passing test case.
</Note>

In 2.0 the failed rows sample was stored and shown only when a test result was `Failed`. In 2.1 it is
also kept and shown when a test **passes** while still finding failed rows, which happens when a failure
threshold tolerates them. Expect failed-row samples on test cases that previously showed none.

## Unsafe Pandas Expressions Fail the Test

<Warning>
**Behavioural.** Affects data quality tests that run on data lake and file sources, where expressions
are evaluated with pandas.
</Warning>

Expressions you write in a test (custom SQL query, partition expression, rule library expressions and
the column name in the inserted-row-count test) are now checked before they run. An expression that
calls functions or reads attributes is no longer executed. The test fails instead, and a custom metric
with such an expression is skipped with a warning. Rewrite these expressions as plain comparisons.

## Failure Thresholds and Dimension Roll-Up on Test Definitions

<Info>
**Additive.** Defaults keep existing tests behaving as before.
</Info>

The built-in column and table tests (for example not-null, unique, in-set, between, regex, row count and
column count) gain optional parameters:

| Parameter | What it does | Default |
| --- | --- | --- |
| `threshold` | Number of failures tolerated before the test fails | `0` |
| `thresholdUnit` | Read `threshold` as `ABSOLUTE` rows or a `PERCENTAGE` of evaluated rows | `ABSOLUTE` |
| `dimensionFailurePolicy` | `OVERALL_ONLY`, or `ANY_DIMENSION` to fail the test as soon as one dimension fails | `OVERALL_ONLY` |
| `minRowsPerDimension` | Under `ANY_DIMENSION` with a percentage threshold, groups with fewer rows are reported but cannot fail the test (only on tests that support it) | `0` |

The upgrade adds these parameters to the definitions you already have. Other test definition updates:

- `tableDiff` gains `parallelQueries` (default `1`) to run several comparison queries at once.
- The numeric column tests now list `NUMERIC` as a supported data type, so they appear for Snowflake and
  DB2 numeric columns.
- The upgrade restores missing `columnName`, `rangeType` and `rangeInterval` parameters on
  `tableRowInsertedCountToBeBetween` for deployments that lost them, and adds the `operator` and
  `partitionExpression` parameters of the custom SQL test where they were missing.

## Test Results, Incidents and Bulk Actions

<Info>
**Additive.**
</Info>

- Test case results gain `duration`, `errorDetails` (type, message and stack trace of an aborted run) and
  a richer `evaluationScope` that says whether the run used a sample or a partition. Dimension results
  gain `minBound`, `maxBound` and `excludedFromRollUp`.
- Incidents gain a `failureSummary`, an incident summary table for faster listing, and a grouping
  endpoint (`/testCaseIncidentStatus/incidentGroups`) that groups open incidents by table, test
  definition or owner. The upgrade backfills the summary table from existing incident history.
- A new request schema, `BundleSuiteBulkRemoveRequest`, describes removing several test cases from a
  logical test suite in one call.
- Data Insights data-asset charts now exclude test cases from totals, so the data-asset total and its
  entity type breakdown keep reconciling. The upgrade updates the stored chart definitions.

## Profiler and Sampling Settings

<Warning>
**Breaking for stored or scripted configuration.** Removed field: `sampleDataStorageConfig`.
</Warning>

External S3 storage for sample data was removed, and with it the `sampleDataStorageConfig` property from
connection and profiler schemas. Because those schemas reject unknown fields, any configuration that
still contains this key fails validation. The upgrade strips the key from stored services, database and
schema profiler settings, version history and saved test connection requests. If you manage connections
or profiler settings as code, remove the key from your files.

For Python code, the module `metadata.profiler.processor.sample_data_handler` is removed, including
`upload_sample_data`, `upload_to_storage`, `validate_path_pattern` and `PathPatternException`. Remove any import
of these names from custom profiler code.

A profiler workflow must also name its database service. In 2.0, a profiler configuration without
`source.serviceName` scanned every table available in the data source and looked each one up in OpenMetadata.
That mode is removed, along with `metadata.profiler.source.metadata_ext`. Set `source.serviceName` in
profiler YAML and Python configurations.

The auto-classification `sampleDataCount` now has a maximum of `1000`. The upgrade lowers any saved
pipeline above that to `1000`. Lower the value in your own configuration files so they still validate.
