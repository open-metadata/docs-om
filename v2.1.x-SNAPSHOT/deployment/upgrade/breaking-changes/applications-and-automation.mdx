# Applications & Automation

The 2.1 upgrade rewrites the stored configuration of the Search Indexing and Data Retention applications
and changes how applications create alerts. If you manage application configuration as code, read this
before you replay it.

## Applications No Longer Create Alerts From Their Definition

<Warning>
**Breaking for custom application definitions, behavioral for existing alerts.** Affects anyone who
publishes their own application definition and admins who relied on the alerts an application installed.
</Warning>

The `eventSubscriptions` list is removed from the application marketplace definition and from the
request that creates one. An application can still create the alerts it needs in its own code, but
alerts are no longer created from a list in the definition.

What the upgrade does to existing alerts:

- An alert that an application created from its definition is **disabled** and no longer tied to the
  application. It is kept so an admin can review it.
- Alerts that an application creates in its own code are left as they are.
- The stored list of alerts is removed from application records and their version history. The
  application's alerts are now read from its relationships.

<Warning>
If you rely on an alert that an application installed in 2.0, check **Settings** > **Notifications** after
the upgrade. Re-enable the alert there if you still want it. Remove `eventSubscriptions` from any
marketplace definition you create through the API: the create schema rejects unknown fields, so a
request that still sends it is refused.
</Warning>

## MCP Server Changes

<Note>
**Behavioral.** Affects Model Context Protocol (MCP) clients and operators who run the MCP server.
</Note>

- **Unsupported protocol versions get `400`.** A `POST` to `/mcp` whose `MCP-Protocol-Version` header names a
  version the server does not implement now returns `400 Bad Request` with a JSON-RPC `Invalid Request` error that
  lists the supported versions. Before, the server answered normally. `initialize` requests and requests without
  the header are not affected. A client that sent a version it never negotiated now fails.
- **Disabling the MCP Server application stops MCP at once.** You no longer restart the server for it to take
  effect.

<Info>
**Additive.** Client registration stays open by default, so existing clients keep working. Operators can now set
`dynamicClientRegistrationEnabled` to turn off new registrations and `allowedRedirectHosts` to allow only
listed HTTPS hosts. Admins get `GET /api/v1/mcp/clients` to list registered clients and
`DELETE /api/v1/mcp/clients/{clientId}` to remove one. Removing a client deletes its tokens, so its users must
authorize again.
</Info>

## Installing an Application With a Bot Needs an Admin

<Warning>
**Breaking.** Affects non-admin users and automation that create or update applications.
</Warning>

In 2.0, only setting `allowBotImpersonation` to `true` needed an admin. In 2.1, creating or updating an
application also needs an admin whenever a `bot` is set. The call returns `403 Forbidden` for other users.

<Tip>
Run application installs that set a bot from an admin account or an admin-level bot.
</Tip>

## Search Indexing Configuration and Run History Are Reset

<Warning>
**Behavioral.** The migration overwrites your settings and clears run history.
</Warning>

- `appConfiguration.entities` of the Search Indexing application is set to `["all"]`, because the
  reindex now rebuilds every selected index and the 2.1 upgrade adds a new relationship type index and
  a new glossary term mapping. A narrower selection you had is not kept.
- The recorded run history of the Search Indexing and RDF Index applications is deleted. The
  Applications page then shows that Search Indexing must be run once. The RDF status stays at
  rebuilding until an RDF Index run succeeds.

<Tip>
Run the Search Indexing application once after upgrading, then the RDF Index application if you use
RDF. Reapply a narrower `entities` selection afterwards if you need one.
</Tip>

## Data Retention Application Settings

<Warning>
**Behavioral, with one new required field.** Affects scripts that send the full retention configuration.
</Warning>

| Setting | What changed |
| --- | --- |
| `activityCommentsRetentionPeriod` | New, in days. Comments on activity events can now be cleaned up. It is a **required** field of the configuration. The default is `0` (keep forever), and the upgrade adds it to your stored configuration. |
| `workflowRetentionPeriod` | New, in days, default **`30`**. Deletes automation workflow records older than this: the short-lived records left by test connection, query runner and reverse ingestion runs. Use `0` to keep them forever. |

Because `activityCommentsRetentionPeriod` is required, a script that sends the whole configuration
without it can fail validation. Add the field to your scripts.

<Tip>
After the upgrade, automation workflow records older than 30 days are deleted by the Data Retention
application. Set `workflowRetentionPeriod` to `0` if you need to keep them.
</Tip>

## New RDF Inference Application

<Info>
**Additive.** Affects deployments that use RDF.
</Info>

A new application, **RDF Inference Materialization** (`RdfInferenceApp`), is added in 2.1, with a default schedule of every 5 minutes. It computes inferred RDF
conclusions on a schedule. It accepts two settings: `force`
(recompute every rule even when nothing changed, default `false`) and `ruleName` (a rule that must
exist). The run always computes every rule, because rules read each other's results. The RDF Index and
RDF Inference configurations are added to the application configuration union, so generated models that
key on branch position must be regenerated rather than patched by hand.

## Automation Workflow and Application Run Changes

<Info>
**Additive.**
</Info>

- Application run records gain `triggeredBy`, the user who started an on-demand run. It is not set for
  scheduled runs.
- The query runner request accepts `fileIds`, so files uploaded to a chat conversation can be analyzed
  in place of a warehouse service. When you use `fileIds`, the service name and credentials are not
  used.
- The upgrade removes the deleted `sampleDataStorageConfig` key from stored test connection requests.
  For more information, see [Data Quality](/v2.1.x-SNAPSHOT/deployment/upgrade/breaking-changes/data-quality).

## Items From 2.0 Not Repeated Here

Changes to the Data Insights `dataQuality` module, MCP tool contracts, CSV background jobs and the
cache were introduced in 2.0 and are covered in the 2.0 breaking changes. This page lists only what
changes between 2.0 and 2.1.
