# Data Governance

This page covers the following changes when you upgrade from OpenMetadata 2.0 to 2.1:

- Glossaries and ontologies
- Policies and roles
- Workflows
- Domains and data products
- Access governance

Classifications and tags have no governance-model changes in OpenMetadata 2.1. For tag name casing during ingestion,
see [Ingestion & Connectors](/v2.2.x-SNAPSHOT/deployment/upgrade/breaking-changes/ingestion-and-connectors). Task and
approval-task changes are covered on the Collaboration page. For more information, see
[Collaboration: Conversations, Tasks, Announcements, Activity, and Alerts](/v2.2.x-SNAPSHOT/deployment/upgrade/breaking-changes/collaboration).

## Policies and Roles

OpenMetadata 2.1 changes the default policies and roles as follows.

### New Default Policy Rules

<Note>
**Behavioral.** Affects who can run SPARQL Protocol and Resource Description Framework (RDF) Query Language (SPARQL) queries, create context memories, and start conversations.
</Note>

The upgrade adds rules to `DataConsumerPolicy`, the policy behind the **Data Consumer** role. The first two rules are
added only if you have not removed the permission they build on. The conversation rule is always added.

| Rule | What it allows | Added when |
| --- | --- | --- |
| `DataConsumerPolicy-ExecuteSparqlQuery-Rule` | Authenticated users and bots can run read-only SPARQL queries through the agent SPARQL endpoint and the Model Context Protocol (MCP) knowledge-graph tools | An allow rule in the policy still lists `ViewAll` |
| `DataConsumerPolicy-CreateContextMemory-Rule` | Authenticated users can create context memories. The creator owns the memory | An allow rule in the policy still lists `EditDescription` |
| `DataConsumerPolicy-CreateConversation-Rule` | Authenticated users can start conversations and reply | Always |

<Warning>
SPARQL results are not filtered by asset or domain policies. If you restrict who can view assets
through custom policies, delete `DataConsumerPolicy-ExecuteSparqlQuery-Rule` after the upgrade.
If you replaced `DataConsumerPolicy` with your own definition, none of these rules are added for you.
Add them yourself if you want these capabilities for non-admin users.
</Warning>

### Domain-Only Access Is Restricted Further

<Note>
**Behavioral.** Affects users who hold the domain-only access policy.
</Note>

Two deny rules are added to the domain-only access policy:

- `DomainAccessDenyAdministrationRule` stops domain-restricted users from creating, deleting, deploying, or
  editing policies, roles, bots, and applications, regardless of their domain.
- `DomainAccessDenyTeamAndUserRule` stops them from creating, deleting, or editing teams and users that
  belong to no domain, and bot users.

If domain owners in your organization manage roles, bots, or applications, give them a separate role that is not
covered by these rules.

### Bots Can No Longer Impersonate Other Bots

<Note>
**Behavioral.** Affects bots that hold `BotNonAdminImpersonationPolicy`.
</Note>

The upgrade adds a rule, `BotNonAdminImpersonationPolicy-DenyBotUsers`, to this policy. It denies the
`Impersonate` operation when the target is a bot user. A bot that used this policy to impersonate another
bot is refused after the upgrade.

### Ontology Roles and Policy

<Info>
**Additive.** A new `OntologyAuthorPolicy` lets its holders create, edit, delete, and view ontologies,
concepts, properties, axioms, and change sets. The upgrade also attaches `OntologyAuthorPolicy` and `OntologyReviewerPolicy` to the existing `DataSteward` role, so data stewards can author and review ontologies.
</Info>

## Approval-Gated Changes

<Info>
**Additive, and only for workflows you change.** A governance workflow with an event-based trigger can
now hold edits until a reviewer approves them. Nothing is held until you set **Approval Mode** to
**Enforce** on a workflow. For more information, see [Approval-Gated Changes](/v2.2.x-SNAPSHOT/how-to-guides/data-governance/approval-gated-changes).
</Info>

<Note>
**Behavioral once you turn it on.** In an Enforce workflow, a human `PUT`, `PATCH`, CSV import, or bulk
asset change to a watched field is not written. OpenMetadata returns the asset with its approved value
and creates a change request and review task. Bots are never held. Scripts that edit governed assets and
expect the change to appear immediately must wait for approval or run as a bot.
</Note>

This feature adds the following for API users:

- Change requests are served from `/v1/changeRequests`: list by asset or requester, read, list
  revisions and decisions, and withdraw your own pending request.
- The bulk add and remove asset calls on domains and data products are checked by the same approval step and respect
  `dryRun`.
- Resolving a review task takes `changeRequestRevision` and, optionally, per-change `changeDecisions`.

## Glossary and Ontology

The following glossary and ontology changes apply in 2.1.

### Terms Proposed by Automation Go to Review

<Note>
**Behavioral.** Affects the stored `GlossaryTermApprovalWorkflow`.
</Note>

The upgrade adds a branch right after the start of this workflow. A term that an automation proposed
(provider `automation`, such as a term an AI agent suggests) now waits for a person to approve it, in
approval steps of its own. When nobody else can decide, the task is assigned to admins. Every other
term is reviewed as before. If you edited the workflow so that its start has more than one outgoing edge,
the upgrade leaves it alone and an admin must connect the branch.

### Relation Type Usage Response Changed

<Note>
**Breaking.** Affects clients of `GET /v1/glossaryTerms/relationTypes/usage`.
</Note>

In OpenMetadata 2.0, the response was a map of relation type name to count. In OpenMetadata 2.1, it is a list of objects, each with a
`relationshipType` (an entity reference) and a `count`.

```diff
- { "relatedTo": 12, "synonym": 4 }
+ [
+   { "relationshipType": { "name": "relatedTo", "...": "..." }, "count": 12 },
+   { "relationshipType": { "name": "synonym", "...": "..." }, "count": 4 }
+ ]
```

Update any script or dashboard that reads this endpoint.

### In-Process RDF Reasoning Is Removed

<Note>
**Breaking for SPARQL inference settings.** Affects anyone who relied on `inferenceEnabled` or reasoning levels on SPARQL queries.
</Note>

OpenMetadata no longer runs reasoners in its own process. These settings in the RDF configuration are deprecated and ignored:

- `inferenceEnabled`
- `defaultInferenceLevel`
- `cacheInferredTriples`
- `maxInMemoryInferenceTriples`

SPARQL queries use no inference unless they ask for `custom`, which reads materialized
rule output. To keep inference, turn on `materializedInferenceEnabled`, which runs rule-based inference
inside the RDF store.

### New RDF Settings

<Info>
**Additive.** These settings are new in 2.1 and do not change behavior until you change them.
</Info>

| Setting | Default | What it does |
| --- | --- | --- |
| `graphReplaceChunkBytes` | `16777216` | Largest request, in bytes, used to replace a whole named graph, such as an active ontology release. A larger graph is uploaded in chunks. Keep it at or below the Fuseki upload limit |
| `materializedInferenceEnabled` | `false` | Materializes inference rules into per-rule named graphs inside the RDF store, so SPARQL queries can request `custom` inference. Requires Fuseki storage |
| `shaclValidationMode` | `REPORT` | Sets the Shapes Constraint Language (SHACL) validation mode. The shipped configuration file uses `REPORT` |
| `dereferenceableIris` | `false` | Exposes authenticated, content-negotiated redirects for the Internationalized Resource Identifiers (IRIs) that OpenMetadata creates |
| `strictOwlProfile` | `true` | Rejects authored axioms that break the supported Web Ontology Language (OWL) 2 DL profile |
| `aiEnabled` | `false` | Turns on the optional AI-assisted ontology flows. Manual authoring stays available when it is off |
| `federation.enabled` | `false` | Allows federated SPARQL queries. When it is off, every `SERVICE` clause is rejected. `allowedEndpoints` (empty by default) lists the external endpoints that may appear in a `SERVICE` clause |

Use the environment variable `RDF_AI_ENABLED` to turn on `aiEnabled`. The older
`RDF_ASK_COLLATE_ENABLED` still works as a fallback but is deprecated.

### The Bundled Fuseki RDF Store Image Changed

<Note>
**Breaking for the bundled Fuseki.** Affects anyone who runs the RDF store from the OpenMetadata Docker
Compose files or Kubernetes manifests.
</Note>

The bundled Fuseki setup no longer builds its own image. It uses the published image
`openmetadata/fuseki:6.2.0-318ff87`. It differs from OpenMetadata 2.0 in the following ways:

- The admin password variable is `ADMIN_PASSWORD`. `FUSEKI_OPENMETADATA_PASSWORD` is removed.
- New required settings are `FUSEKI_DATASETS=openmetadata,openmetadata_a,openmetadata_b`,
  `FUSEKI_UNION_DEFAULT_GRAPH=true`, and `OPENMETADATA_EXTENSION_ENABLED=true`.
- Data is stored under `/fuseki` in the volume `fuseki-store`. The old layout used `/fuseki-data` in the
  volume `fuseki-tdb2-data`.

If you keep the old volume, the new store starts empty. Move the old data into `/fuseki/databases` first,
or rebuild the graph by running the RDF Index application after the upgrade.

### Only Approved Glossary Terms Can Be Applied Through the API

<Note>
**Breaking for scripts and integrations.** Affects clients that tag assets with glossary terms that are
Draft, In Review, Rejected, or Deprecated.
</Note>

The UI only offers Approved glossary terms when you tag an asset, but OpenMetadata 2.0 let the API apply a term in any
status. In OpenMetadata 2.1, the API rejects a glossary term that is newly applied to an asset or field unless it is
Approved. This applies to the following:

- Create, update, patch, and bulk requests
- Table data models
- The columns API
- The `assets/add` endpoint of a term
- Column bulk-update and CSV import previews

A term that the asset already
holds stays, so a request that sends it back unchanged still succeeds. In a bulk request, a rejected item
fails on its own and the others are saved.

<Note>
Approve the terms your integrations apply, or stop applying terms that are not yet approved.
</Note>

### Moving Glossary Terms and Changing Assets in Bulk

<Note>
**Behavioral.** Affects scripts that call the glossary term move and bulk asset endpoints.
</Note>

- Moving a term needs a parent. Name the new parent with both `id` and `type` in the move request.
  Without it, the call returns `400 Bad Request` with `A move needs the parent the term moves under`. To move a
  term to the top level, name the glossary itself as the parent.
- Bulk asset changes are checked one asset at a time. Adding or removing assets on a glossary term, tag,
  domain, or data product no longer checks one permission for the whole request. Each asset is checked and
  saved like its own edit. Failures are reported per asset, and an asset held by an approval workflow comes
  back as pending.

### Ontology Support

<Info>
**Additive.** The ontology entities and APIs below are new in 2.1, except the two items marked as extensions of 2.0 features. No existing client is affected.
</Info>

The following ontology features are new:

- Ontologies: native ontologies, concepts, properties, axioms, change sets, releases, packs, and bulk jobs
  are new entities with their own APIs
- Import and export (extends a 2.0 feature): `importRdf` also accepts JSON-LD. `GET /v1/glossaries/{id}/exportOntology`
  exports a glossary as Turtle, RDF/XML, N-Triples, or JSON-LD. It works even when RDF storage is off
- Terms (extends a 2.0 feature): glossary terms accept `iri` and `conceptMappings` on create
- Queries: a read-only agent SPARQL endpoint, saved SPARQL queries, and an ontology summary
  at `GET /v1/glossaryTerms/ontology/summary`
- Lists: the term list and search endpoints accept `provider` and `excludeProvider`, and the glossary
  list accepts `domain`

## Domains and Data Products

<Note>
**Behavioral.** Affects clients that read domain and data product assets.
</Note>

The following changes apply to domains:

- The asset list and asset count endpoints for domains now need `ViewBasic` on domains. These endpoints are
  `/v1/domains/{id}/assets`, its by-name variant, and the counts. They also take the caller's own access into account.
- The task list for a domain is limited to tasks the caller can view.

<Info>
**Additive.** `GET /v1/domains` accepts `owners`, `domainType`, `tags`, and `glossaryTerms` filters.
`GET /v1/domains/styles` returns the color and icon of every styled domain and data product.
</Info>

## Governance Workflows

<Info>
**Additive.** Workflow definitions accept a `lifecycle` configuration and two new automated tasks,
`dataCompletenessTask` and `collectMetadataTask`. For more information, see
[Lifecycle Stages](/v2.2.x-SNAPSHOT/api-reference/lifecycle-stages). Existing workflow definitions keep
working without changes.
</Info>

<Note>
**Behavioral.** In an approval task, `expiryTimer.durationVariable` and `expiryTimer.dateVariable` must now
start with a letter or underscore and contain only letters, digits, and underscores. A custom workflow that
uses a name with a dash, a dot, or a leading digit fails validation.
</Note>

### Bot Users Can't Trigger Workflows

<Note>
**Behavioral.** Affects integrations that rely on a bot's changes to start a governance workflow.
</Note>

Bot users can't trigger workflows. A change that a bot makes to an asset doesn't start an event-based workflow. If a script or integration used a bot to start a workflow, make the change as a user instead.

## Java SDK

<Note>
**Breaking for Java SDK users.** The generated enum `org.openmetadata.schema.type.WorkflowTriggerFields` is removed. The list of trigger fields is now a server resource, not a schema type. Remove any import of it.
</Note>

## Data Retention

<Note>
**Behavioral.** Affects the Data Retention application.
</Note>

| Setting | Default | Effect |
| --- | --- | --- |
| `workflowRetentionPeriod` | `30` days | Deletes the short-lived automation workflow records left by test connection, query runner, and reverse ingestion runs. Use `0` to keep them forever |
| `activityCommentsRetentionPeriod` | `0` (keep forever) | Retention for comments on activity events |

<Warning>
The Data Retention application deletes automation workflow records older than 30 days. The deletion cannot
be undone. To keep them longer, set `workflowRetentionPeriod` to a larger value, or `0`, before the first run
after the upgrade.
</Warning>
