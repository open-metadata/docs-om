# Ingest Lineage from dbt

Ingest the lineage information from dbt `manifest.json` file into OpenMetadata.

OpenMetadata extracts the lineage information from the `depends_on` and `compiled_query/compiled_code` keys from the manifest file.

<Note>

To capture lineage, the `compiled_code` field must be present in the `manifest.json` file.
- If `compiled_code` is missing, lineage will **not** be captured for that node.
- To ensure `compiled_code` is populated in your dbt manifest, run the following commands in your dbt project:
  - `dbt compile`
  - `dbt docs generate`

</Note>

### 1. Lineage information from dbt "depends_on" key
Openmetadata fetches the lineage information from the `manifest.json` file. Below is a sample `manifest.json` file node containing lineage information under `node_name->depends_on->nodes`.

```json
"model.jaffle_shop.customers": {
  "compiled": true,
  "resource_type": "model",
  "depends_on": {
      "macros": [],
      "nodes": [
          "model.jaffle_shop.stg_customers",
          "model.jaffle_shop.stg_orders",
          "model.jaffle_shop.stg_payments"
      ]
  }
}
```

For the above case the lineage will be created as shown in below:

### 2. Lineage information from dbt queries
Openmetadata fetches the dbt query information from the `manifest.json` file.

Below is a sample `manifest.json` file node containing dbt query information under `node_name->compiled_code` or `node_name->compiled_sql`.

```json
"model.jaffle_shop.customers": {
  "compiled": true,
  "resource_type": "model",
  "compiled_code": "Query for the model"
}
```

The query from dbt will be parsed by the Lineage parser to extract source and target tables to create the lineage.

The lineage may not be created if the lineage parser is not able to parse the query. Please check the logs for any errors in this case.

## dbt Sources with a Different Table Identifier

In dbt, a source has a logical `name`, which you use in `source()` calls, and an optional `identifier`, which is the name of the physical table in the warehouse. When a source sets an `identifier`, OpenMetadata uses it to find the table, so the source and the lineage that depends on it link to the right table. If the source has no `identifier`, OpenMetadata uses the source `name`.

- **Literal match**: OpenMetadata matches the identifier as written. A `*` or `?` in the identifier is treated as part of the table name, not as a search pattern, so the source does not attach to another table by accident.
- **Models**: Models keep using their alias or name, as before.

```yaml
sources:
  - name: raw
    tables:
      - name: customers
        identifier: raw_customers_v2
```

In this example, OpenMetadata looks for a table named `raw_customers_v2`.

## Map dbt Catalog Names to OpenMetadata Databases

OpenMetadata matches each model in `manifest.json` to a table using the database name that dbt writes into the manifest. That name can differ from the name the connector ingested the table under. For example, `dbt-trino` writes the Trino catalog name (`bq_catalog`) for tables that the BigQuery connector ingests under the GCP project ID (`my-gcp-project`). Without a match, OpenMetadata can't link the dbt model to the table.

Use **Catalog Mapping** in the dbt ingestion configuration to resolve this. Add one entry per catalog:

- **Key**: the database name in the dbt manifest, for example `bq_catalog`. Keys are matched ignoring case.
- **Value**: the database name in OpenMetadata, for example `my-gcp-project`.

In a YAML configuration, set `catalogMapping` under `sourceConfig.config`:

```yaml
sourceConfig:
  config:
    type: DBT
    catalogMapping:
      bq_catalog: my-gcp-project
```

OpenMetadata looks up the tables of a mapped catalog under the mapped database, first in the service you are ingesting and then in any other database service, whether or not **Search Tables Across Databases Services** is enabled. If it finds no table there, it falls back to the database name in the manifest.

When OpenMetadata finds a table, it uses it for lineage, dbt tests, and exposures. It also uses it for the domain, data products, and custom properties set in the model's `meta.openmetadata` block. If no table is found, OpenMetadata logs a warning.
