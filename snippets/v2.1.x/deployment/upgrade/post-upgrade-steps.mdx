## Post-Upgrade Steps

Complete these steps after the upgrade finishes.

### Reindex

Reindex all the entities after the upgrade.

#### With UI

Follow these steps to reindex using the UI.

<Steps>
  <Step title="Open the Search Indexing Application">
    Click the **Profile** icon and go to **Settings** > **Applications**. Then click **Search Indexing**.
  </Step>
  <Step title="Run the Application">
    Select the **Schedule** tab and click **Run now**. Every reindex rebuilds the search indexes from scratch, so the
    application has no **Recreate Indexes** option. The **Entities** field defaults to `All`, which is the setting you need after an upgrade.
  </Step>
</Steps>

For more information, see [Reindexing Search](/v2.1.x/how-to-guides/admin-guide/reindexing-search).

If you use the Resource Description Framework (RDF), run the **RDF Index** application from **Settings** > **Applications** after the search reindex finishes.

#### With Kubernetes

Follow these steps to reindex using the command-line interface (CLI).

<Steps>
  <Step title="List the CronJobs">
    Check the available CronJobs:

    ```bash
    kubectl get cronjobs
    ```

    The output looks similar to this:

    ```text
    NAME           SCHEDULE      TIMEZONE   SUSPEND   ACTIVE   LAST SCHEDULE   AGE
    cron-reindex   0/5 * * * *   <none>     True      0        <none>          31m
    ```
  </Step>
  <Step title="Create a Job from the CronJob">
    Create a one-time job from the `cron-reindex` CronJob. Replace `<job_name>` with a name of your choice.

    ```bash
    kubectl create job --from=cronjob/cron-reindex <job_name>
    ```

    The output looks similar to this:

    ```text
    job.batch/cron-reindex-one created
    ```
  </Step>
  <Step title="Check the Job Status">
    Verify that the job completed:

    ```bash
    kubectl get jobs
    ```

    The output looks similar to this:

    ```text
    NAME               STATUS     COMPLETIONS   DURATION   AGE
    cron-reindex-one   Complete   1/1           20s        109s
    ```
  </Step>
  <Step title="View the Logs">
    Replace `<job_name>` with the name of the job you created:

    ```bash
    kubectl logs job/<job_name>
    ```
  </Step>
</Steps>

### (Optional) Update Your OpenMetadata Ingestion Client

If you run the ingestion workflows externally or use a custom Airflow installation, make sure the Python client
you use matches the OpenMetadata server version.

For example, if you upgrade the server to the version `x.y.z`, update your client with:

```bash
pip install "openmetadata-ingestion[<plugin>]==x.y.z"
```

The `plugin` parameter is a comma-separated list of the sources you want to ingest. For example:

```bash
pip install "openmetadata-ingestion[mysql,snowflake,s3]==x.y.z"
```

You can find specific instructions for each connector in the Connectors section.

If you work with your own Airflow deployment, and not the `openmetadata-ingestion` image, also upgrade
`openmetadata-managed-apis`:

```bash
pip install "openmetadata-managed-apis==x.y.z"
```

### Re-Deploy Ingestion Pipelines

Re-deploy your ingestion pipelines so that they run with the upgraded server. Ingestion pipelines appear as agents in the UI.

#### With UI

Follow these steps to re-deploy the agents using the UI.

<Steps>
  <Step title="Open the Service">
    Go to **Connections** > **Databases** and open the service. Repeat these steps for every service that has agents, including the other service types, such as **Dashboards** or **Messaging**.
  </Step>
  <Step title="Open the Metadata Agents">
    Click the **Agents** tab.
  </Step>
  <Step title="Re-Deploy the Agent">
    Click the **⋮** menu next to the agent and select **Re-deploy**. You need edit permission on the service.
  </Step>
</Steps>

To re-deploy every service pipeline at once, run `sh openmetadata-ops.sh deploy-pipelines`. For more information, see [The `openmetadata-ops` Script](#the-openmetadata-ops-script).

#### With Kubernetes

Follow these steps to deploy the pipelines using the CLI.

<Steps>
  <Step title="List the CronJobs">
    Check the available CronJobs:

  </Step>
  <Step title="Create a Job from the CronJob">

  <Step title="View the Logs">

    ```bash
    kubectl logs job/<job_name>
    ```
  </Step>
</Steps>

## The `openmetadata-ops` Script

The `openmetadata-ops` script manages and migrates the database and the search indexes, reindexes existing data into
Elasticsearch or OpenSearch, and re-deploys service pipelines.

### Usage

The script is in the `bootstrap` directory of your OpenMetadata installation. Its general form is:

```bash
sh openmetadata-ops.sh [-dhV] [COMMAND]
```

### Commands

The table lists the most common commands.

<Warning>
`drop-create` permanently deletes all tables and metadata in the configured database. Never run it as part of a normal upgrade. `drop-indexes` removes all search indexes, and `db-tune` with `--apply` changes the database. Back up your database before you run any of these commands.
</Warning>

| Command | What it does |
| --- | --- |
| `info` | Shows the migrations that are applied and the ones waiting to be applied on the target database |
| `migrate` | Migrates the OpenMetadata database schema and search index mappings |
| `validate` | Checks that all the migrations have been applied on the target database |
| `repair` | Repairs the `SERVER_MIGRATION_SQL_LOGS` and `SERVER_CHANGE_LOG` tables, which track the migrations. It removes the entries of failed migrations and updates the checksum of migrations that were already applied |
| `changelog` | Prints the change log of the database migrations |
| `check-connection` | Checks that a connection to the target database can be obtained |
| `drop-create` | Deletes every table in the configured database, creates new tables for the current version of OpenMetadata, and re-creates the search indexes |
| `reindex` | Reindexes data into the search engine from the command line |
| `reindex-rdf` | Reindexes all the entities into the RDF triple store |
| `create-indexes` | Creates the indexes in Elasticsearch or OpenSearch |
| `drop-indexes` | Drops all the indexes from Elasticsearch or OpenSearch |
| `deploy-pipelines` | Deploys all the service pipelines |
| `migrate-secrets` | Migrates secrets from the database to the configured Secrets Manager. It does not support migrating between external Secrets Managers |
| `regenerate-bot-tokens` | Regenerates the JSON Web Token (JWT) of every bot user, then re-deploys the deployed ingestion pipelines. Use it after you rotate the JWT signing keys, change the cluster name, or need to replace leaked tokens |
| `adopt-deployment-config` | Replaces the stored values of a setting with the values from the configuration file and environment of the process that runs it. Run it where the server environment is available, for example inside a server pod |
| `analyze-tables` | Analyzes the database tables of every entity |
| `db-tune` | Generates a per-table tuning report for the database. It only reads by default. Pass `--apply` to run the statements it suggests |
| `relationshipCleanup` | Finds orphaned entity relationships. It runs as a dry run by default |
| `tagUsageCleanup` | Finds orphaned tag usages. It runs as a dry run by default |
| `cleanup-flowable-history` | Cleans up old workflow deployments and history. It runs as a dry run by default |

### Examples

Display the help message:

```bash
sh openmetadata-ops.sh --help
```

Migrate the database schema and search index mappings:

```bash
sh openmetadata-ops.sh migrate
```

Reindex data into the search engine:

```bash
sh openmetadata-ops.sh reindex
```
