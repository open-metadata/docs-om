# Create a Test Case

Create a new test case by linking a test definition to a specific table or column with concrete parameter values.

The server associates the test case with the basic suite of the table in `entityLink`, creating that suite if needed. Omit `testSuite` from the create request. Automatically created suites are named `<tableFQN>.testSuite`. An existing basic suite keeps its name.

## Body Parameters

<ParamField body="name" type="string" required>
  Name of the test case. Must be unique within the target entity scope.
</ParamField>

<ParamField body="testDefinition" type="string" required>
  Fully qualified name (FQN) of the test definition to use. For example, `columnValueMaxToBeBetween`. For a custom SQL test case, use the name of the custom test definition, such as `columnValuesMaxLength`. For more information, see [Custom SQL Test Cases](#custom-sql-test-cases).
</ParamField>

<ParamField body="entityLink" type="string" required>
  Entity link to the target table or column. Format: `<#E::table::tableFQN>` for table-level or `<#E::table::tableFQN::columns::colName>` for column-level.
</ParamField>

<ParamField body="parameterValues" type="array">
  Array of parameter name/value pairs as defined by the test definition.

  <Expandable title="properties">
    <ParamField body="name" type="string" required>
      Parameter name. Must match a parameter in the test definition.
    </ParamField>

    <ParamField body="value" type="string" required>
      Parameter value. Always provide it as a string.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body="description" type="string">
  Description of the test case in Markdown format.
</ParamField>

<ParamField body="displayName" type="string">
  Human-readable display name for the test case.
</ParamField>

<ParamField body="reviewers" type="array">
  Array of reviewer references (users or teams). Each item accepts the same fields as `owners`.
</ParamField>

<ParamField body="computePassedFailedRowCount" type="boolean">
  Compute the passed and failed row count for the test case. Defaults to `false`.
</ParamField>

<ParamField body="useDynamicAssertion" type="boolean">
  Use dynamic assertion to evaluate the test case, if the test definition supports it. Defaults to `false`.
</ParamField>

<ParamField body="dimensionColumns" type="array">
  Names of the columns to group test results by. When set, the test runs overall and grouped by these columns. Defaults to `[]`.
</ParamField>

<ParamField body="topDimensions" type="integer">
  Number of top dimension values to show before the rest are grouped as `Others`. Accepts 1 to 50. Defaults to 5.
</ParamField>

<ParamField body="owners" type="array">
  Array of owner references (users or teams) to assign.

  <Expandable title="properties">
    <ParamField body="id" type="string">
      UUID of the owner entity.
    </ParamField>

    <ParamField body="type" type="string">
      Owner entity type, such as `user` or `team`.
    </ParamField>

    <ParamField body="name" type="string">
      Name of the owner entity.
    </ParamField>
  </Expandable>
</ParamField>

<RequestExample dropdown>
```python POST /v1/dataQuality/testCases
from metadata.sdk import configure
from metadata.sdk.entities import TestCases
from metadata.generated.schema.api.tests.createTestCase import CreateTestCaseRequest

configure(
    host="https://your-company.open-metadata.org/api",
    jwt_token="your-jwt-token"
)

# Create a column-level test case
request = CreateTestCaseRequest(
    name="column_value_max_to_be_between",
    testDefinition="columnValueMaxToBeBetween",
    entityLink="<#E::table::sample_data.ecommerce_db.shopify.dim_address::columns::shop_id>",
    parameterValues=[
        {"name": "minValueForMaxInCol", "value": "1"},
        {"name": "maxValueForMaxInCol", "value": "100"}
    ],
    description="Validates shop_id max value stays between 1 and 100"
)

test_case = TestCases.create(request)
print(f"Created: {test_case.fullyQualifiedName.root}")
```

## Create or Update (PUT)

Use `PUT /v1/dataQuality/testCases` instead of `POST` to perform an upsert. If a test case with the same `fullyQualifiedName` already exists, the server updates it. Otherwise, the server creates a new test case. `PUT` accepts the same body parameters as `POST`, including the optional `description` field. Both curl examples include `description`.

```bash
curl -X PUT "{base_url}/api/v1/dataQuality/testCases" \
  -H "Authorization: Bearer {access_token}" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "column_value_max_to_be_between",
    "testDefinition": "columnValueMaxToBeBetween",
    "entityLink": "<#E::table::sample_data.ecommerce_db.shopify.dim_address::columns::shop_id>",
    "parameterValues": [
      {"name": "minValueForMaxInCol", "value": "1"},
      {"name": "maxValueForMaxInCol", "value": "100"}
    ],
    "description": "Validates shop_id max value stays between 1 and 100"
  }'
```

`PUT` updates an existing entity instead of returning a `409` conflict error.

## Custom SQL Test Cases

A test case passes values to a SQL-based test definition through `parameterValues`. The server rejects any parameter that the test definition doesn't declare in `parameterDefinition`, and requires every parameter marked `required`.

The built-in `tableCustomSQLQuery` test definition runs a SQL query against a table. It accepts these parameters:

| Parameter | Required | Description |
|-----------|----------|-------------|
| `sqlExpression` | Yes | SQL query to run against the table. |
| `strategy` | No | `ROWS` runs the query as written. `COUNT` runs it as a `COUNT` query. Defaults to `ROWS`. |
| `operator` | No | Comparison between the query result and `threshold`: `==`, `>`, `>=`, `<`, `<=`, or `!=`. |
| `threshold` | No | Value to compare the result against. Defaults to `0`. |
| `partitionExpression` | No | Partition expression used to compute the passed and failed row count when `computePassedFailedRowCount` is enabled. |

```bash
curl -X POST "{base_url}/api/v1/dataQuality/testCases" \
  -H "Authorization: Bearer {access_token}" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "orders_no_negative_amounts",
    "testDefinition": "tableCustomSQLQuery",
    "entityLink": "<#E::table::sample_data.ecommerce_db.shopify.orders>",
    "parameterValues": [
      {"name": "sqlExpression", "value": "SELECT * FROM orders WHERE amount < 0"},
      {"name": "strategy", "value": "ROWS"}
    ],
    "computePassedFailedRowCount": true
  }'
```

### Test Cases for a Custom Test Definition

A test case for a custom SQL test definition sets `testDefinition` to the definition's name and passes one `parameterValues` entry per `{{ paramName }}` placeholder. The following request uses the `columnValuesMaxLength` definition, which declares `maxLength`:

```bash
curl -X POST "{base_url}/api/v1/dataQuality/testCases" \
  -H "Authorization: Bearer {access_token}" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "email_max_length",
    "testDefinition": "columnValuesMaxLength",
    "entityLink": "<#E::table::sample_data.ecommerce_db.shopify.dim_address::columns::email>",
    "parameterValues": [
      {"name": "maxLength", "value": "50"}
    ],
    "computePassedFailedRowCount": true
  }'
```

- **Pass condition**: The test case passes only when the number of rows the SQL returns is 0.
- **Row counts**: Set `computePassedFailedRowCount` to `true` to report passed and failed row counts.

For more information, see [Create a Test Definition](/v2.0.x/api-reference/data-quality/test-definitions/create#custom-sql-test-definitions).

## Error Handling

| Code | Error Type | Description |
|------|-----------|-------------|
| `400` | `BAD_REQUEST` | Invalid request body or missing required fields |
| `401` | `UNAUTHORIZED` | Invalid or missing authentication token |
| `403` | `FORBIDDEN` | User lacks permission to create test cases |
| `409` | `ENTITY_ALREADY_EXISTS` | Test case with same name already exists for this entity (POST only) |
