# Create and Manage Templates

This guide walks you through the complete workflow of creating, configuring, and managing notification templates in OpenMetadata.

In OpenMetadata, notification templates are managed through the REST API. There is no template editor in the UI, so you create, update, preview, and delete templates with the `/api/v1/notificationTemplates` endpoints. For the exact request and response format, see the OpenMetadata API documentation (the Swagger UI on your server).

## Creating a Custom Template

Create a notification template by sending a `POST` request to the `/api/v1/notificationTemplates` API. Provide the template fields described in [Filling in Template Details](#filling-in-template-details): the name, subject, and body are required, and the display name and description are optional.

A subscription uses a template by referencing it by name. If a subscription references no template, the system default template applies. See [Linking Templates to Event Subscriptions](#linking-templates-to-event-subscriptions).

### Filling in Template Details

##### Name (Required)
A unique identifier for the template used internally.

**Example**: `high-priority-alerts`, `test-failure-notification`, `schema-change-alerts`

- Use lowercase with hyphens for clarity
- Keep it concise and descriptive

##### Description (Optional)
Document when and why this template should be used.

**Example**: `Send notifications when critical test cases fail. Used with real-time test subscriptions.`

##### Subject (Required)
The email subject line or notification title.

**Constraints**: Maximum 256 characters

**Example**:
```
[{{publisherName}}] - {{camelCaseToTitle event.entityType}} Updated: {{entity.fullyQualifiedName}}
```

This renders to: `[Data Alerts] - Table Updated: database.schema.customers`

<Tip>
Keep subjects concise (under 100 characters) as they appear in email clients where space is limited.
</Tip>

##### Body (Required)
The main template content in HTML with Handlebars.

**Constraints**: Maximum 10,240 characters

**Example**:
```html
<strong>{{event.userName}}</strong> updated <strong>{{camelCaseToTitle event.entityType}}</strong>:
<a href="{{buildEntityUrl event.entityType entity}}">{{entity.fullyQualifiedName}}</a>

{{#if changes.updates}}
<h3>Updated Fields:</h3>
<ul>
  {{#each (limit changes.updates 10)}}
  <li>{{name}}</li>
  {{/each}}
</ul>
{{/if}}
```

#### Submit the Template

1. Review all fields for accuracy.
2. Send the `POST` request to `/api/v1/notificationTemplates`.
3. On success, the template is available for use in event subscriptions.

## Modifying Templates

### Editing User Templates

User templates (those you created) can be fully edited. Update the template through the `/api/v1/notificationTemplates` API with the modified fields (Name, Display Name, Description, Subject, Body).

Changes take effect immediately for any subscriptions using the template.

### Editing System Templates

System templates (pre-built by OpenMetadata) can be partially edited:

- You can modify: Subject and Body
- You cannot modify: Name and Display Name
- System templates track if you've customized them

**Important**: If you don't customize a system template, it automatically updates when OpenMetadata releases improvements. Once you customize it, you're responsible for maintaining it.

## Linking Templates to Event Subscriptions

Templates become useful when connected to event subscriptions. A subscription references the template it uses by name.

### Step 1: Choose the Subscription

Create a new subscription or edit an existing one.

### Step 2: Reference a Template

Set the subscription's notification template to the template you want to use:

- **System templates** - Pre-built templates for common entity types
- **User templates** - Custom templates you've created
- **(unset)** - Use default formatting per channel

### Step 3: Configure Other Settings

Complete the rest of the subscription setup:
- **Event type** - Which changes trigger the notification
- **Destinations** - Where to send notifications (email, Slack, Teams, etc.)
- **Filters** - Optional conditions for when to send

### Step 4: Save the Subscription

Your template is now active and will be used for all notifications from this subscription.


## Showing Failed Rows in a Data Quality Alert

Test case alerts use the default **Entity Updated Notification** template, not a separate data quality template. The default template already shows the failed row count and a table of failed rows, so if your alert uses it, steps 1 to 3 below are all you need. Step 4 is only for alerts that use a custom template.

To show failed rows in an alert:

1. In the test settings, turn on **Compute Row Count**. The failed row count and sample aren't available when this option is off.
2. Check that the test type collects a sample. Only these tests do: Column Values To Be Between, Column Values To Be In Set, Column Values To Be Not In Set, Column Values To Be Not Null, Column Values To Be Unique, Column Values To Match Regex Pattern, Column Values To Not Match Regex, Column Value Lengths To Be Between, and Custom SQL Query. Other tests don't produce a table.
3. Under **Settings** > **Preferences** > **Profiler Configuration**, check that **Enable Storing of Sample Data** is on. It is on by default. When it is off, no sample is collected.
4. If your alert uses a custom template, add the snippet below to the template body. In OpenMetadata, custom templates are created and edited through the API (`/api/v1/notificationTemplates`).
5. Run a test that fails.
6. In the resulting notification, confirm that the failed row count and sample table appear.

The snippet below shows the failed row count and a table of up to 10 columns and 3 failed rows, with the tested column in bold:

```handlebars
{{#with (groupEventChanges event.changeDescription) as |changes|}}
{{#if (and (eq event.entityType 'testCase') (hasFieldInChanges changes 'testCaseResult'))}}
{{#if entity.testCaseResult.failedRows}}Failed rows: {{entity.testCaseResult.failedRows}} ({{math entity.testCaseResult.failedRowsPercentage 'round' 2}}%){{/if}}
{{#with (parseEntityLink entity.entityLink) as |link|}}{{{renderTableSample entity.failedRowsSample link.arrayField 10 3}}}{{/with}}
{{/if}}
{{/with}}
```

Copy all six lines. The first two make the block appear only when a new test result arrives, and the last two close them.

The sample only appears when the test fails.

OpenMetadata masks columns tagged `PII.Sensitive` in the sample. If the table has the `PII.Sensitive` tag, OpenMetadata masks every column.

Previewing a template with the `/api/v1/notificationTemplates/render` API uses sample data without a failed result or failed-row sample, so the failed rows part stays empty. To see it, run a test that fails and check the actual notification.

For more information about configuring the table output, see the [Custom Helpers Reference](/v2.0.x/how-to-guides/data-quality-observability/alerts-notifications/notification-templates/custom-helpers-reference).


## Template Preview and Testing

### Previewing Templates

Before deploying a template to production, preview it to see how it looks. Call the `/api/v1/notificationTemplates/render` API. It renders the template with sample data and returns the formatted output, so you can review it and adjust before using the template.

<Tip>
Preview a template with the render API before you use it, to catch formatting issues early.
</Tip>

### Testing with Real Data

OpenMetadata has no in-product test-send action. To verify a template with real data, trigger an event that matches the subscription, for example run a test that fails for a test case alert, then check the destination.

Checking a real notification helps you:
- Verify links and dynamic content render correctly
- Check channel-specific formatting
- Confirm delivery to your actual notification destinations

## Modifying vs. Duplicating Templates

### When to Modify

Modify a template when you want to update all existing subscriptions using it:

- Impact: All active subscriptions using this template immediately get new formatting
- Use when: Improving a template everyone already uses

### When to Duplicate

Create a new template based on an existing one when:

- You want a variation for a specific use case
- You want to test changes before affecting production subscriptions
- Different teams need different formatting

**How to duplicate**:

There is no automatic duplicate action, so:
1. Copy the template content.
2. Create a new template through the API with a new name.
3. Use the copied content as a starting point.
4. Modify as needed.

## Deleting Templates

### Delete User Templates

Delete a user template you created by sending a `DELETE` request to the `/api/v1/notificationTemplates` API.

**Note**: If the template is actively used in subscriptions, consider what will happen to those subscriptions when you delete it.

### System Templates

System templates cannot be deleted; they're read-only by default.

If you've customized a system template and want to revert to the original, reset it through the API. After resetting, the template again stays synchronized with the OpenMetadata-provided system default, unless you modify it again.

## Troubleshooting Template Issues

### Template Request Fails

**Common causes**:
- Body exceeds 10,240 characters - simplify the content
- Subject exceeds 256 characters - shorten the subject
- Invalid Handlebars syntax - check brackets are balanced
- Required fields are empty - fill in Name, Subject, and Body

### Notifications Not Using Template

**Check**:
1. Is the template referenced in the subscription settings?
2. Is the subscription active?
3. For system templates, do the subscription's event type and entity type match your template name?

### Template Shows Wrong Data

**Check**:
1. Are you using the correct property names? See [Template Context Reference](/v2.0.x/how-to-guides/data-quality-observability/alerts-notifications/notification-templates/template-context-reference)
2. Is the data available for this entity type?
3. Are you using conditionals for optional fields?
